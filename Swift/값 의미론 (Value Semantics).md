# 값 의미론 (Value Semantics)
어떤 변수의 값을 바꿀 수 있는 경로가 그 변수 자신뿐인 성질. 복사본은 완전히 독립적이다.
[[선언형 UI (Declarative UI)]]의 기반 개념이고, [[Diffing]]이 성립하는 이유다.

### 왜 필요한가

없으면(모든 게 참조라면) **내가 변경하지 않았음에도 값이 바뀔 수 있다** — 원격 작용.

1. **지역 추론 붕괴** — 변수의 현재 값을 알려면 같은 객체를 가리키는 모든 참조의 역사를 추적해야 한다
2. **방어적 복사의 만연** — Obj-C의 `@property (copy) NSString *`이 이 문제의 수동 땜질.
   `strong`이면 `NSMutableString`(가변 서브클래스)을 받아 호출자가 나중에 원격 변경할 수 있다.
   Swift는 `String`이 struct라 대입이 곧 복사 → 검문소가 언어에 내장
3. **데이터 레이스** — 공유된 가변 데이터는 스레드 간 레이스 후보. 값은 복사되어 건너가므로
   [[Sendable]]이 값 타입에 거의 공짜로 주어진다

### 내부 동작

두 층으로 나뉜다.

**① 단순 struct** — 대입·인자 전달 시 비트 그대로 복사. 저장 위치는 지역 변수면 스택,
클래스 프로퍼티면 그 객체 안(힙)에 인라인. **"값 타입 = 무조건 스택"이 아니다** — 저장 위치는
구현 세부사항이고, 값 의미론은 저장 위치가 아니라 복사본의 독립성 문제다.

**② 가변 크기 struct (Array, String, Dictionary)** — struct 본체는 힙 버퍼를 가리키는
참조를 품고 있다. 복사 시점이 지연된다 = copy-on-write.

```
var b = a          ① 헤더(몇 워드)만 복사. 버퍼는 공유 → O(1)
b.append(0)        ② 변경 직전 버퍼의 참조 카운트 확인
                      ├─ 1 (나 혼자)  → 복사 없이 제자리 수정
                      └─ 2+ (공유 중) → 이때만 버퍼 복사 후 수정
```

**복사 조건 = 변경 × 공유.** 둘 중 하나만으로는 복사가 일어나지 않는다
(대입만 = 공유일 뿐 변경 없음 / 혼자 변경 = 변경일 뿐 공유 없음).

> 확인 수단은 공개 API `isKnownUniquelyReferenced`. 단, Array가 내부에서 정확히
> 어떻게 쓰는지는 구현 세부사항이다. — WWDC16 "Understanding Swift Performance"

### 대안과 트레이드오프

| 대안 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| 참조 의미론 (class) | identity, 공유가 기능, 복사 비용 없음 | 지역 추론, 방어적 복사 필요, 스레드 안전 부담 |
| 불변 참조 타입 (Java String 등) | 복사 없이 값 의미론 (바뀔 수 없어 공유가 안 보임) | 변경하려면 새 객체 생성 |
| CoW | 값 의미론 + 참조 수준의 복사 비용 | 구현 복잡도, 변경 시 참조 카운트 확인 비용 |

**CoW는 제3의 의미론이 아니라 구현 기법이다.** 의미론(계약) 층에서는 100% 값 의미론이고,
구현 층에서만 참조를 공유한다. 의미론과 구현의 분리.

### 언제 쓰면 안 되는가

- **공유가 목적일 때** — 쓰기가 일어나면 그 즉시 두 개의 메모리로 갈라져 서로 공유하지 못한다.
  여러 곳에서 같은 것을 보고 바꿔야 하면(identity가 필요하면) 참조 타입이 맞다
- **값 타입인데 참조를 품을 때 (주의)** — struct라 복사돼도 안의 class 참조는 같은 객체를
  가리키므로 값 의미론이 깨질 수 있다. 아래 "기반 개념" 참고

### SwiftUI diff와의 관계

body가 만드는 뷰 값 트리는 값이므로 **이전 트리가 독립된 값으로 자동으로 살아남는다.**
살아남은 이전 값과 새 값을 비교해 달라진 부분만 반영하는 것이 [[Diffing]]이다.

뷰가 **가변** class였다면 — **값을 비교할 수는 있지만 이전 값과 비교가 불가능하다.**
변경이 참조하고 있는 모든 곳에서 동시에 일어나 '이전'이 이미 덮어써져 있기 때문이다.
비교 **능력**(`==`, `isEqual`)이 없어서가 아니라 비교 **대상**(과거)이 소멸해서 diff가 무너진다.

**막는 것은 class가 아니라 "변경 가능한 공유 참조"다.** 불변 class(React 엘리먼트, Flutter
위젯)는 변경 자체가 불가능해 과거가 보존되므로 diff가 성립한다 — 위 트레이드오프 표의
"불변 참조 타입" 행과 같은 원리다 ([[값으로서의 View (View as Value)]]).

### 기반 개념

> **값 의미론 = 복사본 사이에 "관찰 가능한 가변 공유"가 없다는 보장.**
> 공유해도, 참조를 품어도 된다 — 그 공유가 복사본의 눈에 띄지만 않으면.

**값 타입 ≠ 값 의미론.** 양방향 모두 성립하지 않는다:

```swift
struct Car { var name: String; var engine: Engine }   // Engine은 가변 class
var b = a            // struct라 복사됐지만
b.engine.power = 999 // 안의 Engine을 공유하고 있어서
a.engine.power       // → 999. 값 의미론이 아니다
```

| 경우 | 참조 품음? | 값 의미론? | 이유 |
| --- | --- | --- | --- |
| Car + 가변 Engine | O | X | 공유된 Engine의 변경이 복사본에서 관찰됨 |
| Array + 힙 버퍼 | O | O | **공유와 변경 시점이 엄연히 다르다** — 공유 중엔 불변, 변경 시엔 독점 |
| Car + 불변 Engine (`let`) | O | O | 공유하지만 바뀔 수 없어 관찰 안 됨 |

언어 차원의 받침: 대입·전달 시 복사된다는 **언어의 복사 규칙**,
"값을 바꾸는 경로는 그 변수뿐"을 강제하는 **배타적 접근**(SE-0176).
