# ARC (Automatic Reference Counting)
힙에 올라간 인스턴스의 수명을 강한 참조가 몇 개인가라는 정수 하나로 관리하는 자동 메모리 관리 방식. 컴파일러가 `retain`/`release`를 코드에 심고, 런타임이 그 카운트를 원자적으로 증감해 0이 되는 순간 해제한다.

### 왜 필요한가

해제를 결정하려는 개발자 앞에서 알 수 있는 것과 알아야 하는 것이 어긋나 있다.

```
내가 아는 것     : "나는 이 객체를 다 썼다"        ← 지역 정보
해제하려면 알 것  : "나 말고 아무도 안 쓴다"        ← 전역 정보
```

누가 어디서 사용하고 있는지 모르기 때문이다. 판단은 코드 한 줄 앞에서 지역적으로 내려야 하는데 근거는 프로그램 전체에 흩어져 있다. 이 비지역성 때문에 실패가 양방향으로 난다.

| 너무 일찍 해제                                      | 영영 해제 안 함               |
| --------------------------------------------- | ----------------------- |
| 그 주소에 값이 없어 크래시. <br>혹은 이미 새 객체가 할당돼 전혀 다른 동작 | 메모리 누수 → 천천히 부풀다 OOM 종료 |

ARC의 기여는 전역에 흩어진 소유권 정보를 카운트 하나로 요약해 지역화한 것이다. 알아서 해제해 준다는 설명과는 다르다. 각 참조는 자기 출입만 신고하면 되고, 마지막인지는 카운터가 안다.

> MRR 시절 Objective-C는 같은 문제를 `alloc`/`new`/`copy`로 시작하는 메서드가 반환한 객체는 호출자가 소유한다는 명명 규칙으로 때웠다. 컴파일러가 검사하지 않는 사회적 계약이었다.

### 내부 동작

#### 카운트는 어디에 저장되는가

```
힙의 인스턴스
┌────────────────┬──────────────┬────────────────┐
│ 타입 메타데이터    │  refCounts   │  저장 프로퍼티    │
│   포인터 (8B)    │    (8B)      │                │
└────────────────┴──────────────┴────────────────┘
        │                │
        │                └─ strong / unowned 카운트, side table 비트
        └─ [[메서드 디스패치 (Method Dispatch)]]의 vtable·witness table로 가는 출발점
```

메타데이터 포인터로 표를 찾아가고(디스패치), 바로 옆 워드에서 카운트를 센다(ARC). 두 노트가 같은 헤더의 이웃한 두 워드에서 만난다.

#### retain/release는 누가, 언제 심는가

ARC는 감시자가 아니라 편집자다. GC가 실행 중 순찰하는 경비원이라면, ARC는 빌드할 때 원고에 지시문을 적어 넣는 편집자다. 앱이 도는 동안 ARC라는 무언가가 도는 시간은 0이고, 실행되는 것은 평범한 함수 호출뿐이다.

```swift
func run() {
    let a = Person()   // ① retain 없음 — init이 이미 +1로 반환한다
    let b = a          // ② swift_retain(a) → 2
    use(b)             // ③ 없음 — @guaranteed 관례
}                      // ④ swift_release ×2 → 0 → deinit → free
```

늘리는 쪽보다 줄이는 쪽(④)이 중요하다. 0이 되는 순간 `deinit`이 돌고 해제 연쇄가 시작된다.

> 위 코드는 실제로는 retain/release가 통째로 사라진다. `b`의 수명이 `a` 안에 완전히 들어가 있어 SIL 최적화 패스가 쌍을 제거한다. 컴파일러 구현 세부라 버전에 따라 달라질 수 있다.

#### 소유권 관례 (+0 / +1)

| | 기본 관례 | 의미 |
| --- | --- | --- |
| 함수 인자 | `@guaranteed` (+0) | 호출하는 동안 호출자가 살려둠. 피호출자는 세지 않음 |
| 반환값 | `@owned` (+1) | 받는 쪽이 소유권을 넘겨받음. `init`이 retain 없이 1로 시작하는 이유 |

인자를 +1로 넘겼다면 호출 한 번에 원자적 연산이 두 번씩 붙는다. 이미 안전한데 한 번 더 안전하다는 걸 처리하는 셈이라 순수한 낭비다. `use(b)`가 도는 동안 호출자가 이미 강하게 참조하고 있어 카운트가 0이 될 수 없기 때문이다. 객체를 누가 만들었는지는 상관없다. 중요한 건 호출 구간 내내 강한 참조가 유지되는가다.

> 이 관례 때문에 컴파일러의 수명 단축 최적화가 예상보다 일찍 객체를 죽이는 경우가 생긴다. 탈출구가 `withExtendedLifetime`이다.

### ARC가 붙는 기준

기준은 **저장 위치가 아니라 수명의 주인**이다. "값 타입은 스택, 참조 타입은 힙"으로는 설명되지 않는다.

```swift
struct Point { var x, y: Double }
class Box { var p: Point }     // p는 힙에 있다. 그런데 ARC는 관여하지 않는다
```

```
스택 지역 변수   함수 진입 ──────── 함수 종료     스코프가 양 끝을 다 안다
Box 안의 p      Box 생성 ───────── Box 소멸      수명이 Box에 매여 있다
힙 인스턴스      생성 ─── ? ? ? ─── 언제?        시작만 안다. 끝은 아무도 모른다
```

수명이 스코프에 매여 있거나 남의 수명에 얹혀 있으면 셀 필요가 없다. `p`의 수명이 `Box`로 매여 있으니 `Box`만 세면 `p`는 저절로 관리된다. **자기 수명을 자기가 갖고 여러 곳에서 공유될 수 있을 때만** 카운터가 필요하다.

#### 값 타입인데 참조 카운트가 등장하는 경우

`Array` 같은 CoW 컬렉션이 그렇다. [[값 의미론 (Value Semantics)]]

`Array` 값 자체는 스코프에 매여 있어 필요 없다. 힙 버퍼는 여러 `Array` 값이 공유할 수 있어 언제 수명이 끝날지 모른다. 카운터는 여기 붙는다.

값 타입이냐 참조 타입이냐는 애초에 질문이 아니었다.

### 순환 참조

계수기는 숫자만 세고 이름을 적지 않는다. 요약하면서 버린 정보가 두 가지 문제로 돌아온다.

두 객체가 서로를 강하게 붙잡으면 카운트가 영원히 0이 안 된다. 누수다. 누수가 났을 때 누가 붙잡고 있는지는 카운트만 봐서는 알 수 없다. Xcode Memory Graph Debugger와 Instruments Leaks가 바깥에서 객체 그래프를 통째로 찍어, ARC가 버린 정보를 복원해 준다.

실무에서는 escaping 클로저가 `self`를 캡처하고 `self`가 그 클로저를 저장하는 구조에서 반복된다. `delegate`를 strong으로 선언했을 때, 부모와 자식이 서로를 링크할 때, `Timer(target:selector:)`를 쓸 때도 마찬가지다.

#### weak

- 반드시 Optional이어야 한다. 컴파일러가 강제한다. 내 의지와 무관하게 값이 사라질 수 있다는 사실이 타입에 드러나야 하기 때문이다.
- 네이티브 `weak`은 객체를 직접 가리키지 않고 side table을 가리킨다. 객체가 죽어도 테이블은 남고, 변수를 읽는 순간 플래그를 확인해 `nil`을 돌려준다.

> 런타임은 weak 변수들을 찾아다니며 지우지 않는다. 읽을 때 판정하는(lazy) 방식이다. side table은 첫 weak 참조가 생길 때 게을리 할당되므로 weak을 쓰지 않는 객체는 이 비용을 내지 않는다. Objective-C는 반대로 전역 weak 해시 테이블을 두고 `dealloc` 시점에 등록된 포인터들을 찾아가서 직접 nil로 민다. 둘 다 공개 API가 아닌 구현 세부다.

#### unowned

옵셔널이 아니다. `?`도 `!`도 없고 언래핑도 없다. "이 참조를 쓰는 동안 대상은 반드시 살아 있다"는 **개발자의 보증**이다.

보증이 깨지면 nil 언래핑으로 죽지 않는다. 런타임이 약속 위반을 잡아서 죽인다. `unowned(safe)`는 strong과 별개인 unowned 카운트를 하나 더 쓴다. 그래서 strong이 0이 되면 `deinit`은 돌지만 할당은 반납하지 않고 살아있지만 죽어있는 좀비 상태로 남긴다. 그 좀비를 읽으면 트랩한다.

```
weak     : 대상 해제 → 읽으면 nil      → 안전한 경로로 계속 흐른다
unowned  : 대상 해제 → 읽으면 즉시 트랩  → 그 자리에서 멈춘다
```

대상이 나보다 먼저 죽을 수 있으면 `weak`, 나와 같이 죽거나 더 오래 살면 `unowned`을 쓴다. 애매하면 `weak`이 안전하다.

옵셔널성과 소유권은 직교하는 두 축이다. `var x: Person!`은 옵셔널이지만 강한 참조라 순환을 못 끊는다. Swift 5부터 `unowned var x: Person?`도 쓸 수 있지만, 그 `?`는 "애초에 없을 수도 있다"는 뜻일 뿐이다. "해제되면 nil이 된다"는 뜻으로 읽으면 오해다.

> `unowned(unsafe)`(= ObjC의 `__unsafe_unretained`)는 아무 장부도 쓰지 않아 진짜 공짜지만 해제된 메모리를 읽는 미정의 동작이다.

### 비용

헤더 8바이트는 본체가 아니다. 진짜 비용은 넷이다.

본체는 원자적 연산이다. `count += 1`은 읽기·더하기·쓰기 세 동작이라 두 스레드가 겹치면 데이터 레이스로 증가 하나가 누락된다. 그러면 카운트가 실제보다 일찍 0에 도달해 아직 쓰는 쪽이 있는데 해제된다. ARC의 존재 이유 자체가 무너진다. 그래서 쪼갤 수 없는 하드웨어 명령이어야 하고 일반 덧셈보다 몇 배 비싸다. 멀티코어에서는 더 나빠진다. 원자적 연산은 해당 캐시 라인의 독점 소유권을 요구하므로, 카운트 값을 아무도 읽지 않아도 객체를 공유했다는 사실만으로 코어 사이에 캐시 라인이 오간다.

다음은 최적화 방해다. `release`는 `deinit`이라는 임의의 사용자 코드를 실행할 수 있다. 컴파일러는 그 지점 이후의 메모리 상태를 가정할 수 없어 중복 로드 제거·죽은 저장 제거·루프 밖 코드 이동이 막힌다. 힙 할당을 스택으로 승격시키는 최적화도 무산된다. 게다가 retain/release 쌍은 같은 함수 안에 나란히 보여야 상쇄되므로, 인라인되지 않는 호출이나 [[메서드 디스패치 (Method Dispatch)]]의 동적 디스패치가 끼면 지우지 못한다. 힙 할당·참조 카운팅·동적 디스패치는 독립돼 있지 않고 서로를 붙잡고 있다.

CoW 오작동은 실무에서 손해가 가장 크게 나는 곳이다. CoW는 쓰기 직전 `isKnownUniquelyReferenced`로 **카운트가 정확히 1인가**를 확인한다.

```
카운트 1 → 나 혼자 쓴다 → 그 자리에서 고친다.               O(1)
카운트 2 → 남도 본다    → 100만 개 전부 복사한 뒤 고친다.     O(n)
```

지우지 못한 retain 하나가 카운트를 1에서 2로 만들면 다음 쓰기 한 줄이 O(1)에서 O(n)으로 폭발한다. 굳이 복사해야만 하는 이유는, 공유 중인 버퍼를 그대로 고치면 다른 곳에서 참조하는 값이 같이 변해 값 의미론이 깨지기 때문이다.

마지막은 해제 연쇄다. 0이 되면 `deinit`이 돌고 그 프로퍼티들이 release되고 걔들도 0이 되면 또 `deinit`이 돈다. 큰 객체 그래프의 루트를 놓는 순간 수천 개가 한 프레임 안에서 연쇄 해제될 수 있다. GC는 이를 분산하지만 ARC는 그 자리에서 다 한다.

### 대안과 트레이드오프

비교하는 것은 이 객체가 아직 쓰이는지 모른 채 접근해 크래시가 나거나 영영 해제되지 않는 문제의 해법들이다. 답을 언제 구하는가, 런타임 비용, 개발자 부담, 해제 시점의 예측 가능성을 놓고 본다.

| 대안                                 | 얻는 것                        | 잃는 것                                      |
| ---------------------------------- | -------------------------- | ---------------------------------------- |
| **수동 (MRR, C)**                    | 완전한 제어, 런타임 장부 없음           | 사람이 비지역 판단을 해야 함, leak과 use-after-free    |
| **추적 GC** (Java, Go)               | 순환 참조도 수거, 개발자 부담 0         | 실행 중 스레드 점유·일시정지, 해제 시점 비결정적, 메모리 여유분 필요  |
| **ARC**                            | 결정적 해제, pause 없음, 메타데이터 적음  | 순환 참조 못 잡음, 원자적 연산, 해제 연쇄 hitch           |
| **컴파일 타임 소유권** (Rust, `~Copyable`) | 런타임 비용 0, 카운터도 원자적 연산도 없음   | 컴파일러를 납득시켜야 함. 학습 곡선, 표현 제약. 순환은 여전히 못 막음 |

앞의 셋은 전부 실행 중에 답을 구하고, 마지막 하나만 실행 전에 구한다.

ARC의 결정적 해제는 낮게 보기 쉽다. 카운트가 0일 때 바로 해제 작업이 시작되므로 파일 핸들·락·소켓을 `deinit`에서 놓는 패턴이 그냥 성립한다. GC 언어는 이게 불가능해서 `try-with-resources`, `defer`, `IDisposable` 같은 별도 장치를 언어 차원에서 따로 마련해야 했다.

SE-0377 `borrowing`/`consuming`과 SE-0390 `~Copyable`은 카운팅이 필요 없는 영역을 넓히는 것이고, 평범한 `class`는 앞으로도 ARC로 관리된다. Swift가 ARC를 버리는 중은 아니다.

### 언제 쓰면 안 되는가

ARC는 끌 수 없으니 쓰지 않는 선택지는 없다. 대신 한계에 닿는 조건을 알고 피한다.

순환 참조가 생기는 구조에서는 카운트 규칙을 성실히 지켜도 절대 0이 안 된다. `weak`/`unowned`로 고리를 끊어야 한다.

- 뜨거운 루프에서 참조 타입을 다루면 원자적 연산과 힙 할당이 쌓임. 값 타입으로 바꿀 수 있으면 바꿀 것. [[값으로서의 View (View as Value)]]의 struct 선택이 정확히 이 판단.
- 여러 스레드가 같은 객체를 공유하면 캐시 라인 경합. 코어별로 나눠 갖는 설계가 나음.
- 큰 CoW 컬렉션 주변에서는 의도치 않은 공유 하나가 O(n) 복사를 부름.
- 큰 객체 그래프를 한 번에 놓으면 해제 연쇄로 프레임이 밀림.

`unowned`를 수명 보장 없이 쓰면 안전한 nil 대신 크래시로 갚는다.

### 실전 적용

카운트는 누가 붙잡았는지를 모르므로, 누수가 의심되면 Memory Graph Debugger로 그래프를 찍어 붙잡고 있는 주체를 찾는다. `deinit`에 로그를 넣어 호출 여부부터 확인하는 것도 빠르다.

escaping 클로저가 `self`를 캡처하고 `self`가 그 클로저를 보유하면 고리가 닫힌다. `[weak self]`가 기본이고, 수명이 보장될 때만 `[unowned self]`를 쓴다. [[클로저 (Closure)]]

`delegate`는 `weak var`로 잡는다. 부모가 자식을 소유하는 구조에서 자식이 부모를 강하게 잡으면 안 된다.

CoW 성능 문제라면 예상 밖의 복사가 보일 때 "이 버퍼를 누가 또 붙잡고 있는가"부터 의심한다.

### 더 파볼 질문

- `withExtendedLifetime`이 필요한 구체적 상황 — 수명 단축 최적화가 언제 예상을 배신하는가
- side table의 정확한 구조와 unowned 카운트가 실제로 쓰이는 경로
- ARC와 [[Swift_Concurrency]] — actor 격리 아래에서 카운팅 비용이 달라지는가
- `borrowing`/`consuming`을 실제 코드에 적용하면 어디까지 카운팅이 사라지는가
- 컴파일러가 retain/release 쌍을 지우는 조건 — 어떤 코드 모양이 최적화를 막는가
