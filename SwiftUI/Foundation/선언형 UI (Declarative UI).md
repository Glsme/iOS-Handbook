# 선언형 UI (Declarative UI)
화면을 상태에 대한 함수로 기술하는 방식. `UI = f(state)`. [[SwiftUI]]의 모든 설계 결정이 여기서 파생된다.

```swift
// 명령형 — 화면을 바꾸는 "명령"을 순서대로 내린다
label.text = "\(count)"
label.isHidden = (count == 0)

// 선언형 — 상태에 따른 "결과"를 기술한다
if count > 0 { Text("\(count)") }
```

### 왜 필요한가

편의의 문제가 아니라 **버그의 한 종류를 구조적으로 없애는** 문제다.

명령형에서 화면의 현재 모습은 상태가 아니라 **지금까지 내린 명령의 누적 결과**다.
그래서 개발자가 작성하는 것은 상태가 아니라 **전이(transition)** 가 된다.

```
상태 3개(isLoading, hasError, isEmpty) → 조합 2³
개발자가 써야 하는 건 조합이 아니라 전이 (이벤트 × 갱신 대상)

로딩 시작 → 스피너 켜고 · 에러뷰 숨기고 · 빈상태뷰 숨기고 · 리스트 숨기고
에러 발생 → 스피너 끄고 · 에러뷰 켜고 · ...
새로고침  → ...
```

각 이벤트 핸들러에서 **모든 뷰를 빠짐없이** 갱신해야 하고, 하나만 빠뜨리면 화면 불일치다.
이 버그의 고약한 성질은 **같은 상태인데 도달 경로에 따라 화면이 다르다**는 것 —
"새로고침 두 번 하면 스피너가 안 사라진다" 류의 재현 어려운 버그가 정확히 이것이다.

선언형은 전이를 개발자 손에서 **뺏는다**.

| | 개발자가 쓰는 것 | 프레임워크가 하는 것 |
| --- | --- | --- |
| 명령형 | 전이 전부 | 없음 |
| 선언형 | 각 상태의 결과 모습만 | 전이 계산 |

빠뜨릴 전이가 없으니 이 종류의 버그가 **불가능**해진다.
"편해진다"가 아니라 **"틀릴 수 없게 된다"** 가 본질이다.

### 내부 동작

```
① 상태 변경
② 그 상태에 의존하는 뷰만 무효화     ← 전체 트리가 아니다
③ body 재호출 → 뷰의 "설명서"를 새로 생성
④ 이전 설명서와 비교(Diffing)
⑤ 달라진 부분만 렌더 트리에 반영
```

**핵심: body 호출 ≠ 화면 갱신.** body는 자주 호출되지만 실제 렌더는 diff 결과가 있을 때만이다.
body 호출이 곧 화면 변경이라면 diff는 존재할 이유가 없다 — **diff의 존재 자체가 둘이 분리돼 있다는 증거다.**

```swift
@State private var count = 1
var body: some View { Text(count > 0 ? "있음" : "없음") }
// count 1 → 2: 상태가 바뀌어 body는 호출되지만, 설명서는 이전과 동일 → 화면은 그대로
```

**무효화(어느 body를 부를지)는 의존성으로 정하고, 렌더(화면을 바꿀지)는 diff로 정한다.**
다른 단계, 다른 기준이다.

**body가 반환하는 건 화면이 아니라 화면의 설명서다.**

```swift
var body: some View {
	VStack { Text("hi"); Button("+") {} }
}
// 실제 반환 타입: VStack<TupleView<(Text, Button)>>
// 이 값은 아무것도 그리지 않는다. 그냥 값이다.
```

여기서 [[Identity]]와 [[Diffing]]이 왜 필요한지가 나온다 —
매번 새로 만들어지는 값들 사이에서 "이번 Text가 저번 Text와 같은 것인가"를 판단해야 하기 때문이다.

> ②의 의존성 추적을 담당하는 구현체는 `AttributeGraph`라는 **비공개 프레임워크**다.
> 크래시 로그·런타임에서 관찰되는 이름일 뿐 공식 API가 아니므로, 이 이름을 근거로 동작을 단정하면 안 된다.
> Apple은 WWDC21 "Demystify SwiftUI"에서 dependency graph라는 말로 개념만 설명한다.

> ⑤의 최종 렌더는 대부분 CoreAnimation 레이어로 직접 그려지고 일부만 UIKit 뷰로 백킹된다
> (`TextField` ↔ `UITextField` 등). 뷰 디버거로 관찰되는 구현 사실이며 API 계약이 아니다.

### 대안과 트레이드오프

대안은 2개가 아니라 스펙트럼이다. 가운데 두 개가 실무에서 가장 흔하다.

```
순수 명령형        UIKit + 수동 갱신
명령형 + 바인딩    UIKit + Combine/RxSwift + MVVM   ← 상태→UI만 선언적, 제어는 명령형
선언형             SwiftUI
선언형 + 단방향    TCA
```

| 대안 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| 명령형 (UIKit) | 세부 제어, 디버깅 가능성, 버전 안정성 | 전이를 전부 손으로 씀 → 상태 불일치 버그 |
| 명령형 + 바인딩 | 갱신은 자동, 제어는 유지 | 레이어 증가, 바인딩 프레임워크 의존 |
| 선언형 (SwiftUI) | 전이 버그 소멸, 코드량 감소 | 제어권, 디버깅 가능성, 배포 타깃 제약 |

**선언형이 잃는 것들은 전부 "위임의 대가"다.** 결정을 프레임워크에 위임했기 때문에 —
위임한 결정에 **개입할 수 없고**(제어권), 위임한 내부를 **들여다볼 수 없고**(디버깅),
위임받은 쪽의 **발전 속도에 묶인다**(배포 타깃).

- **디버깅 가능성** — "왜 이 뷰가 다시 그려졌는가"를 알기 어렵다. 프레임워크 내부가 블랙박스다
- **성능 튜닝 여지** — 셀 재사용·래스터화에 직접 개입할 수 없다. [[EquatableView]]가 그 우회로 중 하나
- **배포 타깃** — 기능이 OS 버전에 강하게 묶인다 (`NavigationStack` iOS 16+, `@Observable` iOS 17+)
- **API 공백** — 아직 안 되는 영역이 있어 `UIViewRepresentable`로 내려가야 한다

**명령형이 이기는 지점은 "디자인 복잡도"가 아니다.** 커스텀 그리기·전환은 오히려 SwiftUI가 강하다
(`Shape`, `Canvas`, `transition`, `matchedGeometryEffect`). 명령형이 이기는 건 두 축이다.

**정밀한 제어** — 프레임워크가 대신 내리는 결정을 직접 내려야 할 때

| 상황 | UIKit | SwiftUI |
| --- | --- | --- |
| 수만 행 채팅 리스트 | `prepareForReuse`, prefetch 시점, 셀 이탈 시 다운로드 취소 | 재사용 정책에 개입 불가. `LazyVStack`은 재사용이 아니라 지연 생성 |
| 스크롤 연동 헤더 축소·패럴랙스 | `scrollViewDidScroll`에서 매 프레임 `contentOffset` | `GeometryReader`+`PreferenceKey` 우회 (`.scrollPosition` iOS 17+) |
| 바텀시트 드래그 vs 내부 스크롤 | `require(toFail:)`, 동시 인식 delegate 조율 | `simultaneousGesture` 정도, 실패 의존성 표현 불가 |
| 스와이프 진행률을 손가락에 매핑 | `UIViewPropertyAnimator.fractionComplete` 읽고 쓰기 | 상태 A→B 전환 모델이라 중간 스크럽이 직접적이지 않음 |
| 금액 입력 실시간 콤마 + 커서 유지 | `shouldChangeCharactersIn`으로 반영 **전** 가로채기 | 바뀐 **결과**만 받음. 값을 고쳐 쓰면 커서가 튐 |

**예측 가능성** — 왜 그렇게 동작하는지 알 수 있는가

- 성능 원인 규명: UIKit은 호출 스택이 곧 원인. SwiftUI는 `Self._printChanges()`(언더스코어 = 비정식)뿐이고 원인이 프레임워크 내부면 추적이 끊긴다
- 레이아웃 즉시 조회: UIKit은 `layoutIfNeeded()`로 그 자리에서 동기 확정. SwiftUI는 측정값이 한 프레임 늦게 와서 그 값으로 레이아웃을 바꾸면 무한 갱신 루프에 빠진다
- OS 버전 간 회귀: 기본 `List` 스타일·키보드 회피·네비게이션 동작이 메이저 업데이트마다 바뀐 전례가 있다. 이건 **SwiftUI가 아직 젊다**는 비용이라 위 항목들과 성격이 다르다

정직하게: 위 대부분은 **우회로가 있다**. 진짜 비용은 그 우회로가 선언형의 전제를 뚫고 나가는 코드라서
**OS 업데이트 때 가장 먼저 깨진다**는 데 있다.

> **선언형은 흔한 90%를 압도적으로 싸게 만들고, 나머지 10%를 비싸게 만든다.**

### 언제 쓰면 안 되는가

- **특정 시점에 상태를 제어해야 할 때** — SwiftUI에는 UIKit 같은 명확한 뷰 생명주기가 **없다**.
  `onAppear`는 `viewDidAppear`와 1:1 대응이 아니라 "뷰가 렌더 트리에 삽입될 때"이고,
  `LazyVStack`에서는 스크롤 재진입마다 다시 호출될 수 있다.
  더 근본적으로 구조체는 계속 새로 만들어졌다 버려지므로 **"뷰 인스턴스의 수명"이라는 개념 자체가 없다.**
  수명을 갖는 건 뷰가 아니라 **상태**이고, 상태의 수명은 [[Identity]]에 묶인다
- **body에 부작용을 넣을 때** — Apple은 body의 호출 시점·횟수를 보장하지 않는다.
  "한 번 호출되겠지"라고 가정하고 네트워크 호출·카운터 증가·외부 상태 변경을 넣는 순간 예측 불가능해진다.
  부작용은 `.task`, `.onChange(of:)` 같은 **지정된 자리**로
- **본질적으로 명령인 조작** — "지금 이 셀로 스크롤", "이 필드에 포커스"는 명령이다.
  상태로 우회해야 한다 (`ScrollViewReader`, `@FocusState`)
- **Source of truth 이원화** — 같은 데이터를 두 곳에 두면 선언형의 보장이 깨진다. [[DataFlow]]의 첫 번째 원칙
- **body에 무거운 연산** — 자주 호출되므로 즉시 프레임 드랍으로 나타난다

### 실전 적용

선언형은 다섯 개 구성 요소로 구현된다. 다섯이 다 있어야 성립한다.

```swift
struct CounterView: View {          // ① struct — 값 타입
	@State private var count = 0    // ② 프로퍼티 래퍼 — 상태 저장소

	var body: some View {           // ③ body   ④ some View
		VStack {                    // ⑤ @ViewBuilder
			Text("\(count)")
			Button("+") { count += 1 }
		}
	}
}
```

① **struct인 이유** — 설명서는 매 갱신마다 새로 만들어 버리는 **일회용**이다. 초당 수십 번 만들어
버려도 될 만큼 생성 비용이 공짜에 가까워야 이 모델이 성립하고, 스택에 찍어내는 값 타입이 그걸 만족한다

② **[[@State]]가 필요한 이유** — struct는 매번 새로 만들어지므로 상태를 뷰 **안에** 둘 수 없다
(저장하면 다음 생성 때 초기값으로 리셋). 상태는 SwiftUI가 바깥(힙)에서 관리하고 뷰는 참조만 한다.
[[@State]] 노트의 *"Storage는 View 인스턴스가 아닌 View identity에 종속"* 이 정확히 이 얘기다.
그리고 [[@State]]는 저장소이기만 한 게 아니라 **"이 값이 바뀌면 나를 다시 그려라"라는 신고 채널**이다 —
일반 `var`의 변경은 SwiftUI가 알아차릴 방법 자체가 없다

③ **body** — `UI = f(state)`의 `f` 그 자체

④ **`some View`** — 불투명 반환 타입. 실제 타입 `VStack<TupleView<(Text, Button)>>`은 중첩이 폭발해
손으로 못 쓰니 "View를 따르는 어떤 구체 타입 하나"라고만 선언한다.
중요한 건 **타입이 곧 뷰의 구조**라는 점 — SwiftUI는 이 타입 정보로 [[Identity]]와 [[Diffing]]을 한다.
`any View`로 타입을 지우면 이 정보가 사라져 최적화가 깨진다

⑤ **`@ViewBuilder`** — Result Builder. 중괄호 안 나열을 `TupleView` 하나로 합친다.
뷰 안에서 `if/else`가 되는 것도 이것 덕분(`_ConditionalContent`로 변환)

### 기반 개념

`f`가 함수라는 사실이 요구하는 것들. 기억 고리: **"함수라서 셋, 함수로 안 되는 게 하나."**

1. **순수 함수** — 같은 상태 → 항상 같은 화면. body의 계약이 이것이고, "body에 부작용 금지"가 여기서 파생된다
2. **값 의미론** — 뷰가 struct인 이유. 복사본이 독립적으로 존재해 **이전 버전이 자동으로 살아남는 성질**.
   **가변** 참조 타입이면 이전·현재가 같은 객체를 가리켜 비교하려는 순간 비교 대상이 이미 없다
   (불변 class는 변경이 불가능해 과거가 보존되므로 diff가 선다 — Flutter·React가 그 길이다).
   diff는 기반 개념이 아니라 **이 성질 위에서만 도는 기계**다
3. **호출 시점·횟수 비보장** — 언제 몇 번 부를지는 프레임워크가 정하고 개발자는 알 수 없다.
   1번이 body의 **계약**이라면 이건 그 계약을 요구하는 **이유** 쪽이다 —
   호출을 프레임워크가 소유하기 때문에 순수해야만 안전하다
4. **[[Identity]]** — `f`가 함수인 것만으로는 부족하다. 값은 매번 새로 만들어지므로
   "이번 `Text`가 저번 `Text`와 같은 것인가"를 값 자체로는 판단할 수 없다.
   SwiftUI는 **타입 구조 + 트리에서의 위치**로 정하고(structural identity), 부족하면 `.id()`로 명시한다(explicit identity)

**순수 함수 + 값 의미론 + 호출 비보장 + [[Identity]]**, 넷이 함께 있어야 선언형 UI가 성립한다.
앞의 셋은 `f`가 함수라서 따라오고, 마지막 하나는 함수만으로는 안 되는 것이다.
